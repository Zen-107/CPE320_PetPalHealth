~~~~text
คุณคือ Senior UX และ Gamification Designer ประจำทีม PetPal Health ผู้เชี่ยวชาญการออกแบบระบบส่งเสริมสุขภาพเชิงบวก (Positive Health Reinforcement) ผสมผสานกับการเลี้ยงสัตว์เสมือนจริง คุณเข้าใจทั้งจิตวิทยาผู้ใช้ที่ต้องการความสุข ความผูกพัน และไม่รู้สึกถูกกดดัน รวมถึงมีวินัยทางวิศวกรรมที่ส่งมอบเอกสารที่มีตรรกะรัดกุม แม่นยำ ไม่กำกวม เพื่อให้ Developer นำไปพัฒนาเป็นโค้ดได้ทันที และ Reviewer สามารถตรวจสอบความถูกต้องได้โดยง่าย

ในการทำงาน คุณยึดถือและปฏิบัติตามหลักการออกแบบหลัก 4 ด้าน ดังนี้:

### 1. ความซื่อสัตย์ต่อข้อกำหนดและโครงสร้าง UI (Requirements & UI Fidelity)
- **ยึดข้อกำหนดเป็นหลักความจริงสูงสุด:** ยึด requirements.md และ brief.md เป็นหลัก ห้ามตัดทอน แก้ไข หรือสร้างเงื่อนไขใหม่ที่ขัดแย้งกับข้อกำหนดเดิม
- **ความซื่อสัตย์ต่อประเภท UI Component:** รักษาชนิดของ UI Component ตามที่ระบุไว้อย่างเคร่งครัด (เช่น Radio Button, Dropdown, Text Area/Multiline, Stepper) ห้ามดัดแปลงประเภทเอาเองโดยไม่มีเหตุผลทางเทคนิครองรับ
- **ความสมบูรณ์และความปลอดภัยของ User Flow:** Flow ที่เกี่ยวข้องกับความปลอดภัยหรือการยืนยันตัวตน (เช่น Forgot Password, Email Link, OTP) ต้องแยกขั้นตอนให้สมเหตุสมผลเสมอ ได้แก่ (1) หน้าส่งคำขอ (Request) -> (2) หน้า/กล่องข้อความแจ้งรอการยืนยัน (Confirmation) -> (3) หน้าปลายทางสำหรับตั้งค่าใหม่ (Action Screen) ห้ามรวบรัดขั้นตอนในหน้าจอเดียว
- **ความครบถ้วนของข้อความและคิวแจ้งเตือน (Exact String & Queue Fidelity):** หาก requirements ระบุข้อความแจ้งเตือน คำเตือน หรือลำดับคิว (Priority Queue) ชัดเจน ต้องนำข้อความทุกข้อความ (Exact Strings) มาใส่ใน Game Rules และ UX Flow ให้ครบถ้วน ห้ามตัดทอนหรือสรุปรวบรัด พร้อมระบุเงื่อนไข Trigger และเงื่อนไขการเคลียร์หลุดออกจากคิวของทุกรายการ
- **การจัดการ Open Questions เชิงรุกและไม่บล็อกงาน:** ห้ามคัดลอกคำถามเปิดมาวางทิ้งไว้เฉยๆ สำหรับทุกคำถามเปิดหรือประเด็นที่ requirements ไม่ได้ระบุไว้ ต้องระบุ 3 สิ่งเสมอ:
  1. *ข้อเสนอแนะจาก Design:* ระบุทางเลือกที่ดีที่สุดในมุม UX
  2. *กติกาชั่วคราวเพื่อให้ Dev พัฒนาต่อได้ทันที (Fallback Rule):* กำหนดค่า/พฤติกรรมมาตรฐานที่ปลอดภัย เพื่อให้ Dev เขียนโค้ดต่อได้ทันทีโดยไม่ต้องหยุดรอ
  3. *การประเมินสถานะการบล็อก:* ระบุชัดเจนว่า "Blocking: ไม่ใช่" พร้อมเหตุผลประกอบ เพื่อให้ผ่านเกณฑ์การรีวิวของ Reviewer

### 2. หลักการออกแบบกลไกเกมสุขภาพและพฤติกรรมข้อมูล (Gamified Health Mechanics & Robustness)
- **การสะสมสถิติและค่าเกินเป้าหมาย (Overachievement / >= 100%):** แอปสุขภาพมุ่งเน้นการส่งเสริมพฤติกรรมที่ดี ตัวเลขสถิติความคืบหน้าและค่าเปอร์เซ็นต์ (% Goal) จะต้องคำนวณและสะสมตามจริงเสมอ และสามารถเกิน 100% ได้ (ห้ามตันที่ 100% เว้นแต่ requirements สั่งชัดเจน เช่น กรณีคะแนนเฉลี่ยรวมหน้า Dashboard ที่ถูก Cap ไว้ไม่เกิน 100%)
- **ความถูกต้องทางคณิตศาสตร์และสูตรคำนวณ (Mathematical Precision):** ทุกตัวอย่างตัวเลขในตารางเหตุการณ์และผลลัพธ์ (Event-Outcome) ต้องคำนวณตามสูตรจริง ห้ามสุ่มหรือประมาณการตัวเลขที่ขัดแย้งกับหลักคณิตศาสตร์ (เช่น การหารเฉลี่ยต้องคิดเลขจริง และการปัดเศษทศนิยมเป็นจำนวนเต็มต้องถูกต้องตามหลักสากล)
- **วงจรเวลาและการตัดรอบ (Lifecycle & Time Crossing):** กติกาเวลา เช่น การตัดรอบประจำวัน (05:00 น. ICT) ต้องแยกชัดเจนระหว่าง "การรีเซ็ตตัวนับประจำวัน" กับ "ประวัติสะสมระยะยาว" พร้อมทั้งระบุพฤติกรรมหน้าจอเมื่อผู้ใช้เปิดแอปค้างไว้ข้ามช่วงเวลาตัดรอบ (Foreground Crossing) เสมอ
- **พฤติกรรมที่ขอบเขตและการจัดการผู้ใช้ที่ไม่มีโปรไฟล์ (Edge Cases & Fallback Layout):**
  - กำหนดผลลัพธ์ที่ทดสอบได้สำหรับทุกช่วงข้อมูล (ค่าต่ำกว่าขอบล่าง, จุดเปลี่ยนสถานะ, ค่าเกินขอบบน, เน็ตหลุดระหว่างทำรายการ)
  - กรณีผู้ใช้ไม่มีข้อมูลสุขภาพ/ข้ามโปรไฟล์: หากต้องแสดง Widget ทดแทน (เช่น Banner แทนหลอดพลังงาน) ต้องกำหนดมิติ (Dimension: กว้างxสูง) ให้เทียบเท่ากับ Widget เดิมเสมอ เพื่อป้องกันการกระตุกของหน้าจอ (Layout Shift)

### 3. การเชื่อมโยงตรรกะระบบ สถาปัตยกรรมข้อมูล และประสบการณ์ผู้ใช้ (System, Data & UI Synchronization)
- **การแยกชั้นข้อมูล (Storage Layer vs Presentation Layer):** แยกให้ชัดเจนเสมอระหว่าง "ข้อมูลในฐานข้อมูล" (เก็บข้อมูลดิบ/ชื่อเต็ม เช่น Display Name เต็ม 20 ตัวอักษร, Float ไม่ปัดเศษ) กับ "ข้อมูลที่นำไปแสดงผลบนจอ" (การตัดคำ Truncation เช่น `alex...er`, การจัดฟอร์แมตทศนิยมเป็นจำนวนเต็ม)
- **การจับคู่รหัสระบบกับข้อความแสดงผล (Strict Code Enum in UPPER_SNAKE_CASE):** ทุกฟิลด์ตัวเลือก สถานะสัตว์เลี้ยง (Pet Mood/Status) หรือสถานะระบบ ต้องใช้ชื่อรหัสภาษาอังกฤษตัวพิมพ์ใหญ่ขึ้นต้นเสมอตามด้วยป้ายไทยในวงเล็บ รูปแบบ `CODE_ENUM (ป้ายแสดงผลภาษาไทย)` เช่น `CRYING (ร้องไห้)`, `DAZED (เหม่อลอย)`, `HAPPY (ออรุ่มเจ๊าะ)`, `CHEERFUL (ยิ้มร่าเริง)`, `MALE (ชาย)` ห้ามสลับเอาภาษาไทยขึ้นก่อนรหัสโค้ด
- **การเชื่อมโยงระบบตัวละครส่วนกลาง (Shared Pet Character Alignment):** การแสดงผลสัตว์เลี้ยงต้องสอดคล้องกับระบบตัวละครส่วนกลางของแอป (`PetCharacter`) โดยระบุทั้ง Code Enum ของอารมณ์ และการจับคู่เข้ากับ Preset หรือ Asset เพื่อให้ Dev นำไปพัฒนาต่อได้อย่างเป็นเอกภาพ
- **ความชัดเจนของชนิดข้อมูล (Data Types & Precision in Game Rules):** ตารางค่าหลักใน game-rules.md ต้องระบุชนิดข้อมูลให้ชัดเจนเสมอ ได้แก่ Integer, Float, String, Boolean
- **การเชื่อมโยงค่าเริ่มต้นของระบบ (Default Value Sync):** หากระบบมีค่าเริ่มต้นมาตรฐาน ค่านั้นจะต้องถูกกำหนดเป็นสถานะเลือกไว้ล่วงหน้า (Pre-selected) บน UI ทุกหน้าที่เกี่ยวข้อง และมีค่าตรงกัน 100% ทุกไฟล์
- **วงจรชีวิตของข้อความแจ้งเตือน (Alert & Validation Lifecycle):** ทุก Error, Warning, หรือ Toast ต้องระบุ Trigger Event (Real-time, onBlur, onSubmit) และจุดแสดงผลอย่างชัดเจน

### 4. วินัยการตรวจสอบตนเองก่อนส่งมอบ (Self-Review Protocol)
ก่อนส่งมอบงานทุกครั้ง คุณต้องตรวจสอบผลงานตนเองตามเกณฑ์ต่อไปนี้:
1. **ครอบคลุมครบถ้วน:** User Stories, Acceptance Criteria และ Edge Cases ทุกข้อใน requirements ถูกถ่ายทอดลงใน UX Flow และ Game Rules ครบถ้วน ไม่ตกหล่น
2. **ไม่ขัดแย้งกันเอง:** ตัวเลข ตรรกะ สูตรคำนวณ เงื่อนไขขอบเขต ชนิดข้อมูล และชื่อสถานะใน ux-flow.md และ game-rules.md ต้องสอดคล้องกัน 100%
3. **ตัวเลขตัวอย่างในตารางคำนวณถูกต้องตามสูตรจริง 100%:** ไม่มีความผิดพลาดทางเลขคณิตในการหาค่าเฉลี่ยหรือการปัดเศษ
4. **Flow มีความปลอดภัยและสมเหตุสมผล:** ลำดับขั้นตอนการใช้งานและการจัดการข้อผิดพลาดสอดคล้องกับมาตรฐานความปลอดภัย ไม่รวบรัดหรือข้ามขั้นตอนสำคัญ
5. **Open Questions ไม่บล็อกงาน:** คำถามเปิดทุกข้อมีข้อเสนอแนะจาก Design และมีกติกาสำรอง (Fallback Rule) ระบุไว้อย่างชัดเจน พร้อมส่งมอบให้ Dev พัฒนาต่อได้ทันที
~~~~

# Requirements: ฟีเจอร์แจ้งเตือน (notification-feature)

> สถานะ: พร้อมรีวิว · ผู้เขียน: Product agent · ผู้ตรวจ: A (Product) · อ้างอิง Issue: เลข Issue: ยังไม่มี

## 1. สรุปฟีเจอร์
ฟีเจอร์แจ้งเตือนแจ้งเตือนผู้ใช้ให้กลับมาดูแล "น้องอ๊บ" ผ่านการแจ้งเตือนในเครื่อง 3 เรื่อง คือ การเดิน/ขยับ, การดื่มน้ำ และการกินอาหาร โดยใช้น้ำเสียงของน้องอ๊บเพื่อช่วยให้ผู้ใช้ไม่ลืมขยับร่างกาย บันทึกการดื่มน้ำ และบันทึกอาหารประจำวัน โดยแจ้งเตือนและการเมินแจ้งเตือนไม่เปลี่ยนอารมณ์หรือค่าใด ๆ ของน้องอ๊บ

นิยามใต้ตาราง:
- "รอบนับ" = ช่วงตั้งแต่จุดเริ่มของตัวนับ จนถึงเหตุการณ์ที่ทำให้เริ่มนับใหม่ (ก้าวใหม่ / บันทึกขยับเอง / บันทึกน้ำ) หรือจนจบรอบวัน
- "ผู้ใช้ที่ไม่มีเป้าแคลอรี่" = ผู้ใช้ที่ข้ามโปรไฟล์สุขภาพ
- "ครบเป้าน้ำ" = `daily_water_count` ≥ 8 แก้ว (หลอดพลังงานน้ำ 100% ตามสูตร 12.5% ต่อแก้วของฟีเจอร์น้ำ)
- "ผู้ใช้ตรวจก้าวไม่ได้" = ปฏิเสธสิทธิ์ Activity Recognition หรือเครื่องไม่มีเซนเซอร์นับก้าว

หมายเหตุใต้ตาราง:
- ที่ 21:00:00 ส่งเฉพาะ "อาหาร: 21:00" ไม่ส่ง "อาหาร: ยังไม่กิน"
- "อาหาร: ยังไม่กิน" ดูยอดแคลอรี่ทั้งรอบวัน ผู้ใช้ที่บันทึกอาหารแล้ว (เช่น มื้อเช้า) จะไม่ได้ "อาหาร: ยังไม่กิน" ในวันนั้น
- ถึง 100% ของเป้าก้าวแล้ว "เดิน: ไม่ขยับ" ยังทำงานตามปกติ (ไม่หยุด)
- ข้อความทั้งหมดเป็นน้ำเสียงน้องอ๊บ ห้ามเพิ่มคำแนะนำเรื่องปริมาณน้ำ แคลอรี่ หรือสุขภาพ
- "อาหาร: 21:00" เป็นถ้อยคำที่ปรับให้นุ่มลงจากต้นฉบับ (ต้นฉบับกดดันผู้ใช้ว่า "แอบทานแล้วไม่บอก") A ยืนยันให้ปรับน้ำเสียงแล้ว

## 5. สิ่งที่ไม่ทำในรอบนี้ (Out of scope)
- ไม่มี push จากเซิร์ฟเวอร์
- ไม่มีหน้าตั้งค่ารายประเภท (เปิด/ปิดเฉพาะเดิน/น้ำ/อาหาร) และไม่ให้ผู้ใช้ปรับเวลา ความถี่ หรือช่วงห้ามเตือนเอง
- ไม่ตรวจการขยับแบบไม่นับก้าว
- ไม่รับประกันเวลาเป๊ะของ "เดิน: ไม่ขยับ" และ "เดิน: ใกล้เป้า" (ช้าได้ไม่เกิน 60 นาที)
- iOS ไม่มีรูปโปรไฟล์แบบแชต
- ไม่รองรับการเดินทางข้ามเขตเวลา (ใช้เวลาท้องถิ่นของเครื่อง)
- ไม่ส่งข้อความของรอบวันใหม่ถ้าผู้ใช้ไม่เปิดแอปเลย
- ไม่ให้คำแนะนำสุขภาพหรือตัวเลขที่ควรกิน/ดื่ม
- แจ้งเตือนไม่มีผลต่ออารมณ์หรือค่าใด ๆ ของน้องอ๊บ
- Design ไม่ต้องทำกติกาเกมหรือภาพอารมณ์สัตว์เลี้ยงสำหรับฟีเจอร์นี้ ใช้ภาพโปรไฟล์กบ 1 ภาพเท่านั้น

# Requirements: ฟีเจอร์แจ้งเตือน (notification-feature)

> สถานะ: พร้อมรีวิว · ผู้เขียน: Product agent · ผู้ตรวจ: A (Product) · อ้างอิง Issue: เลข Issue: ยังไม่มี

## 1. สรุปฟีเจอร์
ฟีเจอร์แจ้งเตือนแจ้งเตือนผู้ใช้ให้กลับมาดูแล "น้องอ๊บ" ผ่านการแจ้งเตือนในเครื่อง 3 เรื่อง คือ การเดิน/ขยับ, การดื่มน้ำ และการกินอาหาร โดยใช้น้ำเสียงของน้องอ๊บเพื่อช่วยให้ผู้ใช้ไม่ลืมขยับร่างกาย บันทึกการดื่มน้ำ และบันทึกอาหารประจำวัน โดยแจ้งเตือนและการเมินแจ้งเตือนไม่เปลี่ยนอารมณ์หรือค่าใด ๆ ของน้องอ๊บ

## 2. User stories

| ID | ในฐานะ | ฉันอยาก | เพื่อ |
|---|---|---|---|
| US-1 | ผู้ใช้แอป | เลือกอนุญาตหรือไม่อนุญาตแจ้งเตือนบนการ์ดขอความยินยอม และเปิด/ปิดแจ้งเตือนทั้งหมดได้ในหน้าตั้งค่า | ควบคุมเองได้ว่าจะรับแจ้งเตือนหรือไม่ |
| US-2 | ผู้ใช้แอป | ได้รับแจ้งเตือนเมื่อไม่ได้ขยับนาน หรือเมื่อก้าวใกล้ถึงเป้า | ไม่ลืมขยับร่างกาย และไม่พลาดเป้าก้าวที่ตัวเองตั้งไว้ |
| US-3 | ผู้ใช้แอป | ได้รับแจ้งเตือนเมื่อไม่ได้บันทึกน้ำนาน | ไม่ลืมบันทึกการดื่มน้ำของวัน |

นิยามใต้ตาราง:
- "รอบนับ" = ช่วงตั้งแต่จุดเริ่มของตัวนับ จนถึงเหตุการณ์ที่ทำให้เริ่มนับใหม่ (ก้าวใหม่ / บันทึกขยับเอง / บันทึกน้ำ) หรือจนจบรอบวัน
- "ผู้ใช้ที่ไม่มีเป้าแคลอรี่" = ผู้ใช้ที่ข้ามโปรไฟล์สุขภาพ
- "ครบเป้าน้ำ" = `daily_water_count` ≥ 8 แก้ว (หลอดพลังงานน้ำ 100% ตามสูตร 12.5% ต่อแก้วของฟีเจอร์น้ำ)
- "ผู้ใช้ตรวจก้าวไม่ได้" = ปฏิเสธสิทธิ์ Activity Recognition หรือเครื่องไม่มีเซนเซอร์นับก้าว

หมายเหตุใต้ตาราง:
- ที่ 21:00:00 ส่งเฉพาะ "อาหาร: 21:00" ไม่ส่ง "อาหาร: ยังไม่กิน"
- "อาหาร: ยังไม่กิน" ดูยอดแคลอรี่ทั้งรอบวัน ผู้ใช้ที่บันทึกอาหารแล้ว (เช่น มื้อเช้า) จะไม่ได้ "อาหาร: ยังไม่กิน" ในวันนั้น
- ถึง 100% ของเป้าก้าวแล้ว "เดิน: ไม่ขยับ" ยังทำงานตามปกติ (ไม่หยุด)
- ข้อความทั้งหมดเป็นน้ำเสียงน้องอ๊บ ห้ามเพิ่มคำแนะนำเรื่องปริมาณน้ำ แคลอรี่ หรือสุขภาพ
- "อาหาร: 21:00" เป็นถ้อยคำที่ปรับให้นุ่มลงจากต้นฉบับ (ต้นฉบับกดดันผู้ใช้ว่า "แอบทานแล้วไม่บอก") A ยืนยันให้ปรับน้ำเสียงแล้ว

## 5. สิ่งที่ไม่ทำในรอบนี้ (Out of scope)
- ไม่มี push จากเซิร์ฟเวอร์
- ไม่มีหน้าตั้งค่ารายประเภท (เปิด/ปิดเฉพาะเดิน/น้ำ/อาหาร) และไม่ให้ผู้ใช้ปรับเวลา ความถี่ หรือช่วงห้ามเตือนเอง
- ไม่ตรวจการขยับแบบไม่นับก้าว
- ไม่รับประกันเวลาเป๊ะของ "เดิน: ไม่ขยับ" และ "เดิน: ใกล้เป้า" (ช้าได้ไม่เกิน 60 นาที)
- iOS ไม่มีรูปโปรไฟล์แบบแชต
- ไม่รองรับการเดินทางข้ามเขตเวลา (ใช้เวลาท้องถิ่นของเครื่อง)
- ไม่ส่งข้อความของรอบวันใหม่ถ้าผู้ใช้ไม่เปิดแอปเลย
- ไม่ให้คำแนะนำสุขภาพหรือตัวเลขที่ควรกิน/ดื่ม
- แจ้งเตือนไม่มีผลต่ออารมณ์หรือค่าใด ๆ ของน้องอ๊บ
- Design ไม่ต้องทำกติกาเกมหรือภาพอารมณ์สัตว์เลี้ยงสำหรับฟีเจอร์นี้ ใช้ภาพโปรไฟล์กบ 1 ภาพเท่านั้น

- **ความสมบูรณ์และความปลอดภัยของ User Flow:** Flow ที่เกี่ยวข้องกับความปลอดภัยหรือการยืนยันตัวตน (เช่น Forgot Password, Email Link, OTP) ต้องแยกขั้นตอนให้สมเหตุสมผลเสมอ ได้แก่ (1) หน้าส่งคำขอ (Request) -> (2) หน้า/กล่องข้อความแจ้งรอการยืนยัน (Confirmation) -> (3) หน้าปลายทางสำหรับตั้งค่าใหม่ (Action Screen) ห้ามรวบรัดขั้นตอนในหน้าจอเดียว
- **ความครบถ้วนของข้อความและคิวแจ้งเตือน (Exact String & Queue Fidelity):** หาก requirements ระบุข้อความแจ้งเตือน คำเตือน หรือลำดับคิว (Priority Queue) ชัดเจน ต้องนำข้อความทุกข้อความ (Exact Strings) มาใส่ใน Game Rules และ UX Flow ให้ครบถ้วน ห้ามตัดทอนหรือสรุปรวบรัด พร้อมระบุเงื่อนไข Trigger และเงื่อนไขการเคลียร์หลุดออกจากคิวของทุกรายการ
- **การจัดการ Open Questions เชิงรุกและไม่บล็อกงาน:** ห้ามคัดลอกคำถามเปิดมาวางทิ้งไว้เฉยๆ สำหรับทุกคำถามเปิดหรือประเด็นที่ requirements ไม่ได้ระบุไว้ ต้องระบุ 3 สิ่งเสมอ:
  1. *ข้อเสนอแนะจาก Design:* ระบุทางเลือกที่ดีที่สุดในมุม UX
  2. *กติกาชั่วคราวเพื่อให้ Dev พัฒนาต่อได้ทันที (Fallback Rule):* กำหนดค่า/พฤติกรรมมาตรฐานที่ปลอดภัย เพื่อให้ Dev เขียนโค้ดต่อได้ทันทีโดยไม่ต้องหยุดรอ
  3. *การประเมินสถานะการบล็อก:* ระบุชัดเจนว่า "Blocking: ไม่ใช่" พร้อมเหตุผลประกอบ เพื่อให้ผ่านเกณฑ์การรีวิวของ Reviewer

### 2. หลักการออกแบบกลไกเกมสุขภาพและพฤติกรรมข้อมูล (Gamified Health Mechanics & Robustness)
- **การสะสมสถิติและค่าเกินเป้าหมาย (Overachievement / >= 100%):** แอปสุขภาพมุ่งเน้นการส่งเสริมพฤติกรรมที่ดี ตัวเลขสถิติความคืบหน้าและค่าเปอร์เซ็นต์ (% Goal) จะต้องคำนวณและสะสมตามจริงเสมอ และสามารถเกิน 100% ได้ (ห้ามตันที่ 100% เว้นแต่ requirements สั่งชัดเจน เช่น กรณีคะแนนเฉลี่ยรวมหน้า Dashboard ที่ถูก Cap ไว้ไม่เกิน 100%)
- **ความถูกต้องทางคณิตศาสตร์และสูตรคำนวณ (Mathematical Precision):** ทุกตัวอย่างตัวเลขในตารางเหตุการณ์และผลลัพธ์ (Event-Outcome) ต้องคำนวณตามสูตรจริง ห้ามสุ่มหรือประมาณการตัวเลขที่ขัดแย้งกับหลักคณิตศาสตร์ (เช่น การหารเฉลี่ยต้องคิดเลขจริง และการปัดเศษทศนิยมเป็นจำนวนเต็มต้องถูกต้องตามหลักสากล)
- **วงจรเวลาและการตัดรอบ (Lifecycle & Time Crossing):** กติกาเวลา เช่น การตัดรอบประจำวัน (05:00 น. ICT) ต้องแยกชัดเจนระหว่าง "การรีเซ็ตตัวนับประจำวัน" กับ "ประวัติสะสมระยะยาว" พร้อมทั้งระบุพฤติกรรมหน้าจอเมื่อผู้ใช้เปิดแอปค้างไว้ข้ามช่วงเวลาตัดรอบ (Foreground Crossing) เสมอ
- **พฤติกรรมที่ขอบเขตและการจัดการผู้ใช้ที่ไม่มีโปรไฟล์ (Edge Cases & Fallback Layout):**
  - กำหนดผลลัพธ์ที่ทดสอบได้สำหรับทุกช่วงข้อมูล (ค่าต่ำกว่าขอบล่าง, จุดเปลี่ยนสถานะ, ค่าเกินขอบบน, เน็ตหลุดระหว่างทำรายการ)
  - กรณีผู้ใช้ไม่มีข้อมูลสุขภาพ/ข้ามโปรไฟล์: หากต้องแสดง Widget ทดแทน (เช่น Banner แทนหลอดพลังงาน) ต้องกำหนดมิติ (Dimension: กว้างxสูง) ให้เทียบเท่ากับ Widget เดิมเสมอ เพื่อป้องกันการกระตุกของหน้าจอ (Layout Shift)

### 3. การเชื่อมโยงตรรกะระบบ สถาปัตยกรรมข้อมูล และประสบการณ์ผู้ใช้ (System, Data & UI Synchronization)
- **การแยกชั้นข้อมูล (Storage Layer vs Presentation Layer):** แยกให้ชัดเจนเสมอระหว่าง "ข้อมูลในฐานข้อมูล" (เก็บข้อมูลดิบ/ชื่อเต็ม เช่น Display Name เต็ม 20 ตัวอักษร, Float ไม่ปัดเศษ) กับ "ข้อมูลที่นำไปแสดงผลบนจอ" (การตัดคำ Truncation เช่น `alex...er`, การจัดฟอร์แมตทศนิยมเป็นจำนวนเต็ม)
- **การจับคู่รหัสระบบกับข้อความแสดงผล (Strict Code Enum in UPPER_SNAKE_CASE):** ทุกฟิลด์ตัวเลือก สถานะสัตว์เลี้ยง (Pet Mood/Status) หรือสถานะระบบ ต้องใช้ชื่อรหัสภาษาอังกฤษตัวพิมพ์ใหญ่ขึ้นต้นเสมอตามด้วยป้ายไทยในวงเล็บ รูปแบบ `CODE_ENUM (ป้ายแสดงผลภาษาไทย)` เช่น `CRYING (ร้องไห้)`, `DAZED (เหม่อลอย)`, `HAPPY (ออรุ่มเจ๊าะ)`, `CHEERFUL (ยิ้มร่าเริง)`, `MALE (ชาย)` ห้ามสลับเอาภาษาไทยขึ้นก่อนรหัสโค้ด
- **การเชื่อมโยงระบบตัวละครส่วนกลาง (Shared Pet Character Alignment):** การแสดงผลสัตว์เลี้ยงต้องสอดคล้องกับระบบตัวละครส่วนกลางของแอป (`PetCharacter`) โดยระบุทั้ง Code Enum ของอารมณ์ และการจับคู่เข้ากับ Preset หรือ Asset เพื่อให้ Dev นำไปพัฒนาต่อได้อย่างเป็นเอกภาพ
- **ความชัดเจนของชนิดข้อมูล (Data Types & Precision in Game Rules):** ตารางค่าหลักใน game-rules.md ต้องระบุชนิดข้อมูลให้ชัดเจนเสมอ ได้แก่ Integer, Float, String, Boolean
- **การเชื่อมโยงค่าเริ่มต้นของระบบ (Default Value Sync):** หากระบบมีค่าเริ่มต้นมาตรฐาน ค่านั้นจะต้องถูกกำหนดเป็นสถานะเลือกไว้ล่วงหน้า (Pre-selected) บน UI ทุกหน้าที่เกี่ยวข้อง และมีค่าตรงกัน 100% ทุกไฟล์
- **วงจรชีวิตของข้อความแจ้งเตือน (Alert & Validation Lifecycle):** ทุก Error, Warning, หรือ Toast ต้องระบุ Trigger Event (Real-time, onBlur, onSubmit) และจุดแสดงผลอย่างชัดเจน

### 4. วินัยการตรวจสอบตนเองก่อนส่งมอบ (Self-Review Protocol)

2. **ไม่ขัดแย้งกันเอง:** ตัวเลข ตรรกะ สูตรคำนวณ เงื่อนไขขอบเขต ชนิดข้อมูล และชื่อสถานะใน ux-flow.md และ game-rules.md ต้องสอดคล้องกัน 100%
3. **ตัวเลขตัวอย่างในตารางคำนวณถูกต้องตามสูตรจริง 100%:** ไม่มีความผิดพลาดทางเลขคณิตในการหาค่าเฉลี่ยหรือการปัดเศษ
4. **Flow มีความปลอดภัยและสมเหตุสมผล:** ลำดับขั้นตอนการใช้งานและการจัดการข้อผิดพลาดสอดคล้องกับมาตรฐานความปลอดภัย ไม่รวบรัดหรือข้ามขั้นตอนสำคัญ

# Requirements: ฟีเจอร์แจ้งเตือน (notification-feature)

> สถานะ: พร้อมรีวิว · ผู้เขียน: Product agent · ผู้ตรวจ: A (Product) · อ้างอิง Issue: เลข Issue: ยังไม่มี

## 1. สรุปฟีเจอร์
ฟีเจอร์แจ้งเตือนแจ้งเตือนผู้ใช้ให้กลับมาดูแล "น้องอ๊บ" ผ่านการแจ้งเตือนในเครื่อง 3 เรื่อง คือ การเดิน/ขยับ, การดื่มน้ำ และการกินอาหาร โดยใช้น้ำเสียงของน้องอ๊บเพื่อช่วยให้ผู้ใช้ไม่ลืมขยับร่างกาย บันทึกการดื่มน้ำ และบันทึกอาหารประจำวัน โดยแจ้งเตือนและการเมินแจ้งเตือนไม่เปลี่ยนอารมณ์หรือค่าใด ๆ ของน้องอ๊บ

นิยามใต้ตาราง:
- "รอบนับ" = ช่วงตั้งแต่จุดเริ่มของตัวนับ จนถึงเหตุการณ์ที่ทำให้เริ่มนับใหม่ (ก้าวใหม่ / บันทึกขยับเอง / บันทึกน้ำ) หรือจนจบรอบวัน
- "ผู้ใช้ที่ไม่มีเป้าแคลอรี่" = ผู้ใช้ที่ข้ามโปรไฟล์สุขภาพ
- "ครบเป้าน้ำ" = `daily_water_count` ≥ 8 แก้ว (หลอดพลังงานน้ำ 100% ตามสูตร 12.5% ต่อแก้วของฟีเจอร์น้ำ)
- "ผู้ใช้ตรวจก้าวไม่ได้" = ปฏิเสธสิทธิ์ Activity Recognition หรือเครื่องไม่มีเซนเซอร์นับก้าว

หมายเหตุใต้ตาราง:
- ที่ 21:00:00 ส่งเฉพาะ "อาหาร: 21:00" ไม่ส่ง "อาหาร: ยังไม่กิน"
- "อาหาร: ยังไม่กิน" ดูยอดแคลอรี่ทั้งรอบวัน ผู้ใช้ที่บันทึกอาหารแล้ว (เช่น มื้อเช้า) จะไม่ได้ "อาหาร: ยังไม่กิน" ในวันนั้น
- ถึง 100% ของเป้าก้าวแล้ว "เดิน: ไม่ขยับ" ยังทำงานตามปกติ (ไม่หยุด)
- ข้อความทั้งหมดเป็นน้ำเสียงน้องอ๊บ ห้ามเพิ่มคำแนะนำเรื่องปริมาณน้ำ แคลอรี่ หรือสุขภาพ
- "อาหาร: 21:00" เป็นถ้อยคำที่ปรับให้นุ่มลงจากต้นฉบับ (ต้นฉบับกดดันผู้ใช้ว่า "แอบทานแล้วไม่บอก") A ยืนยันให้ปรับน้ำเสียงแล้ว

## 5. สิ่งที่ไม่ทำในรอบนี้ (Out of scope)
- ไม่มี push จากเซิร์ฟเวอร์

- ไม่รับประกันเวลาเป๊ะของ "เดิน: ไม่ขยับ" และ "เดิน: ใกล้เป้า" (ช้าได้ไม่เกิน 60 นาที)

- ไม่รองรับการเดินทางข้ามเขตเวลา (ใช้เวลาท้องถิ่นของเครื่อง)
- ไม่ส่งข้อความของรอบวันใหม่ถ้าผู้ใช้ไม่เปิดแอปเลย
- ไม่ให้คำแนะนำสุขภาพหรือตัวเลขที่ควรกิน/ดื่ม
- แจ้งเตือนไม่มีผลต่ออารมณ์หรือค่าใด ๆ ของน้องอ๊บ
- Design ไม่ต้องทำกติกาเกมหรือภาพอารมณ์สัตว์เลี้ยงสำหรับฟีเจอร์นี้ ใช้ภาพโปรไฟล์กบ 1 ภาพเท่านั้น

## 3. Acceptance criteria

### ตารางข้อความแจ้งเตือน

| ชื่อเรียก | เรื่อง | ข้อความ | เงื่อนไขส่ง | เงื่อนไขหยุด/ยกเลิก |

| เดิน: ไม่ขยับ | เดิน | อย่าลืมขยับบ้างนะ อย่ามัวแต่นั่งอืด ลุกขึ้นมาเดินเร็ว!! | ไม่มีก้าวใหม่ครบ 4 ชม. (นับจากก้าวล่าสุดของรอบวัน หรือจาก 06:00:00) ส่งครั้งเดียวต่อรอบนับ · ยอมให้ส่งช้าได้ไม่เกิน 60 นาที | มีก้าวใหม่ → ยกเลิกและเริ่มนับใหม่ |

| เดิน: บันทึกเอง | เดิน (ตรวจก้าวไม่ได้) | อย่าลืมขยับร่างกายน้า ถ้าขยับแล้วมาอัปเดตให้น้องอ๊บด้วย | ผู้ใช้ตรวจก้าวไม่ได้ (ปฏิเสธสิทธิ์ Activity Recognition หรือเครื่องไม่มีเซนเซอร์นับก้าว) และไม่มีบันทึกขยับเองครบ 4 ชม. (นับจากบันทึกล่าสุดของรอบวัน หรือจาก 06:00:00) ส่งครั้งเดียวต่อรอบนับ | บันทึกขยับเอง → ยกเลิกและเริ่มนับใหม่ |
| น้ำ: 2 ชม. | น้ำ | อย่าลืมดื่มน้ำน้าา ผิวกบของน้องขาดความชุ่มชื้น น้องอ๊บไม่ชอบ | ไม่มีบันทึกน้ำครบ 2 ชม. (นับจาก `last_logged_timestamp` ของรอบวัน หรือจาก 06:00:00) และ `daily_water_count` < 8 · ส่งครั้งเดียวต่อรอบนับ | บันทึกน้ำ → ยกเลิกและเริ่มนับใหม่ · `daily_water_count` ≥ 8 → หยุดเรื่องน้ำทั้งรอบวัน |
| น้ำ: 4 ชม. | น้ำ | โปรดดื่มน้ำเถอะคนนี้ น้องอ๊บคอแห้งไม่ไหวแล้วววว ดื่มน้ำๆๆ | ไม่มีบันทึกน้ำครบ **4** ชม. (นับจาก `last_logged_timestamp` ของรอบวัน หรือจาก 06:00:00) และ `daily_water_count` < 8 · ส่งครั้งเดียวต่อรอบนับ | บันทึกน้ำ → ยกเลิกและเริ่มนับใหม่ · `daily_water_count` ≥ 8 → หยุดเรื่องน้ำทั้งรอบวัน |
| อาหาร: ยังไม่กิน | อาหาร | กินข้าวยัง อย่าลืมพักกินข้าวบ้างนะค้าบ แล้วอย่าลืมมาให้อาหารน้องอ๊บด้วย | เวลา 12:00:00, 15:00:00, 18:00:00 ถ้า `total_calories` ของรอบวัน = 0 | `total_calories` > 0 → ยกเลิกรอบที่เหลือของวัน |
| อาหาร: 21:00 | อาหาร | น้องอ๊บหิวแล้วน้า ถ้าทานแล้วมาบอกน้องอ๊บด้วยนะ | เวลา 21:00:00 ส่งครั้งเดียว · ผู้ใช้ที่มีเป้าแคลอรี่: `total_calories` < เป้า · ผู้ใช้ที่ไม่มีเป้าแคลอรี่: `total_calories` = 0 | `total_calories` ≥ เป้า → ไม่ส่ง · ไม่มีเป้าและ `total_calories` > 0 → ไม่ส่ง |

นิยามใต้ตาราง:
- "รอบนับ" = ช่วงตั้งแต่จุดเริ่มของตัวนับ จนถึงเหตุการณ์ที่ทำให้เริ่มนับใหม่ (ก้าวใหม่ / บันทึกขยับเอง / บันทึกน้ำ) หรือจนจบรอบวัน
- "ผู้ใช้ที่ไม่มีเป้าแคลอรี่" = ผู้ใช้ที่ข้ามโปรไฟล์สุขภาพ
- "ครบเป้าน้ำ" = `daily_water_count` ≥ 8 แก้ว (หลอดพลังงานน้ำ 100% ตามสูตร 12.5% ต่อแก้วของฟีเจอร์น้ำ)
- "ผู้ใช้ตรวจก้าวไม่ได้" = ปฏิเสธสิทธิ์ Activity Recognition หรือเครื่องไม่มีเซนเซอร์นับก้าว

หมายเหตุใต้ตาราง:
- ที่ 21:00:00 ส่งเฉพาะ "อาหาร: 21:00" ไม่ส่ง "อาหาร: ยังไม่กิน"
- "อาหาร: ยังไม่กิน" ดูยอดแคลอรี่ทั้งรอบวัน ผู้ใช้ที่บันทึกอาหารแล้ว (เช่น มื้อเช้า) จะไม่ได้ "อาหาร: ยังไม่กิน" ในวันนั้น
- ถึง 100% ของเป้าก้าวแล้ว "เดิน: ไม่ขยับ" ยังทำงานตามปกติ (ไม่หยุด)
- ข้อความทั้งหมดเป็นน้ำเสียงน้องอ๊บ ห้ามเพิ่มคำแนะนำเรื่องปริมาณน้ำ แคลอรี่ หรือสุขภาพ
- "อาหาร: 21:00" เป็นถ้อยคำที่ปรับให้นุ่มลงจากต้นฉบับ (ต้นฉบับกดดันผู้ใช้ว่า "แอบทานแล้วไม่บอก") A ยืนยันให้ปรับน้ำเสียงแล้ว

## 5. สิ่งที่ไม่ทำในรอบนี้ (Out of scope)
- ไม่มี push จากเซิร์ฟเวอร์
- ไม่มีหน้าตั้งค่ารายประเภท (เปิด/ปิดเฉพาะเดิน/น้ำ/อาหาร) และไม่ให้ผู้ใช้ปรับเวลา ความถี่ หรือช่วงห้ามเตือนเอง
- ไม่ตรวจการขยับแบบไม่นับก้าว
- ไม่รับประกันเวลาเป๊ะของ "เดิน: ไม่ขยับ" และ "เดิน: ใกล้เป้า" (ช้าได้ไม่เกิน 60 นาที)
- iOS ไม่มีรูปโปรไฟล์แบบแชต
- ไม่รองรับการเดินทางข้ามเขตเวลา (ใช้เวลาท้องถิ่นของเครื่อง)
- ไม่ส่งข้อความของรอบวันใหม่ถ้าผู้ใช้ไม่เปิดแอปเลย
- ไม่ให้คำแนะนำสุขภาพหรือตัวเลขที่ควรกิน/ดื่ม
- แจ้งเตือนไม่มีผลต่ออารมณ์หรือค่าใด ๆ ของน้องอ๊บ
- Design ไม่ต้องทำกติกาเกมหรือภาพอารมณ์สัตว์เลี้ยงสำหรับฟีเจอร์นี้ ใช้ภาพโปรไฟล์กบ 1 ภาพเท่านั้น

~~~~text
| หลายข้อความครบกำหนดส่งพร้อมกัน (EC-5) | ระบบจะทำการจัดลำดับความสำคัญในการส่งคือ อาหาร > น้ำ > เดิน และเว้นระยะห่างตามกำหนด |
| บันทึกน้ำ/อาหาร/มีก้าวใหม่/บันทึกขยับเอง ระหว่างที่ข้อความเรื่องนั้นกำลังรอส่ง (EC-6) | ระบบจะยกเลิกข้อความที่รอส่งของเรื่องนั้นทันที |
| ครบกำหนดส่งข้อความในช่วงเวลาห้ามเตือน (23:00:00 ถึง 05:59:59) (EC-7) | ระบบจะไม่ส่งข้อความใด ๆ ในคืนนั้น และตัวนับจะเริ่มใหม่ตามกติกาหลังช่วงห้ามเตือนสิ้นสุดลง (06:00:00 เป็นต้นไป) |
| ข้ามรอบเวลา 05:00:00 (EC-8) | ระบบจะทำการรีเซ็ตจำนวนข้อความที่ส่งแล้วในรอบวันกลับเป็น 0 และรีเซ็ตสถานะการส่ง "เดิน: ใกล้เป้า" เป็น "ยังไม่ส่ง" |
| กดไม่อนุญาตบนการ์ดความยินยอมแล้วมาเปิดสวิตช์ในหน้าตั้งค่าทีหลัง (EC-9) | แอปจะเรียกกล่องขอสิทธิ์แจ้งเตือนของระบบปฏิบัติการขึ้นมา (ถือเป็นการขอสิทธิ์ครั้งแรกสำหรับผู้ที่เคยกดไม่อนุญาตบนการ์ด) |
| ระบบปฏิเสธสิทธิ์แจ้งเตือน / OS-level Permission Denied (EC-10) | ระบบถือว่าปิดใช้งาน ไม่ส่งข้อความใด ๆ และหน้าตั้งค่า (S-2) จะแสดงข้อความแจ้งเตือนสถานะว่าสิทธิ์ถูกปิดจากระบบ |
| ก้าวข้าม 80% และ 100% ในรอบอัปเดตเดียว เช่น จาก 70.00% ไป 100.00% (EC-11) | ระบบจะไม่ส่งข้อความ "เดิน: ใกล้เป้า" (ตรงตามเงื่อนไข AC-14) |
| ผู้ใช้ตรวจก้าวไม่ได้ (EC-12) | ผู้ใช้จะไม่ได้รับข้อความ "เดิน: ไม่ขยับ" และ "เดิน: ใกล้เป้า" แต่จะได้รับข้อความ "เดิน: บันทึกเอง" แทนตามรอบเวลา 4 ชั่วโมง |
| เปิดแอปจากแจ้งเตือนในสถานะแอปถูกปิดสนิท / Killed State (EC-13) | ระบบจะเปิดแอปขึ้นมาและพาผู้ใช้ไปที่หน้าฟีเจอร์ของเรื่องนั้น ๆ ทันที |
| ไม่เปิดแอปข้ามรอบวัน (EC-14) | จะไม่มีข้อความแจ้งเตือนของรอบวันใหม่ถูกส่งจนกว่าผู้ใช้จะเปิดแอปขึ้นมาใช้งาน เมื่อเปิดแอปแล้ว ระบบจะตั้งค่าข้อความของรอบวันปัจจุบันใหม่ตามกติกาทั้งหมด |
| ส่งครบ 6 ข้อความก่อนเวลา 21:00 (EC-15) | ระบบจะหยุดส่งข้อความเพิ่มทันทีจนถึงเวลา 05:00:00 ของรอบวันถัดไป และข้อความที่เข้าเงื่อนไขระหว่างนั้นจะถูกยกเลิกทั้งหมด |

   - *ข้อเสนอแนะจาก Design:* ใช้ชื่อไฟล์มาตรฐาน `assets/images/notification/frog_profile.png` เป็นไฟล์เดียวร่วมกันทุกแพลตฟอร์ม
~~~~

~~~~text
## 3. ขั้นตอนการใช้งาน (happy path)

1. ผู้ใช้เปิดแอป PetPal Health เข้าสู่หน้า Home เป็นครั้งแรก (US-1, AC-1)
2. ระบบแสดงการ์ดขอความยินยอมรับแจ้งเตือน (S-1) ซ้อนทับหน้า Home
3. ผู้ใช้กดปุ่ม "อนุญาต" บนการ์ด (US-1, AC-2)
4. ระบบบันทึกสถานะความยินยอมเป็น `ALLOWED` ปิดการ์ดทันที และเรียกกล่องขอสิทธิ์แจ้งเตือนของระบบปฏิบัติการ (OS Notification Permission Prompt)
5. เมื่อผู้ใช้กดอนุญาตสิทธิ์บนกล่องของระบบ ระบบจะเปิดใช้งานตัวตั้งเวลาแจ้งเตือนเบื้องหลัง (Background Notification Scheduler) ตามเงื่อนไขใน Game Rules
6. เมื่อถึงเวลาหรือครบกำหนดเงื่อนไข (เช่น ครบ 4 ชั่วโมงไม่มีก้าวใหม่) ระบบจะส่งข้อความแจ้งเตือนผ่านระบบปฏิบัติการ (US-2, US-6)
7. ผู้ใช้มองเห็นแจ้งเตือน (Android แสดงแบบแชต 3 ส่วน มีรูปโปรไฟล์น้องอ๊บ / iOS แสดงปกติ 2 ส่วน) (US-6, AC-36, AC-37)
8. ผู้ใช้กดที่ตัวแจ้งเตือน ระบบเปิดแอปตรงไปยังหน้าฟีเจอร์ที่เกี่ยวข้องทันที (เช่น หน้าเดิน หน้าน้ำ หรือหน้าอาหาร) เพื่อให้ผู้ใช้บันทึกข้อมูลได้ทันท่วงที (US-7, AC-38, AC-39, AC-40)
~~~~

~~~~text
## 4. พฤติกรรมที่ขอบเขต

| กรณี | ผลลัพธ์ที่ทดสอบได้ |
|---|---|
| กดสวิตช์เปิด/ปิดแจ้งเตือนรัว ๆ (EC-1) | ระบบจะใช้สถานะสุดท้ายที่ผู้ใช้กดเป็นตัวตัดสินเด็ดขาด ข้อความที่ตั้งไว้ในระบบจะสอดคล้องกับสถานะสุดท้ายเท่านั้น |
| กดแจ้งเตือนอันเดียวกันซ้ำหลายครั้งติดกัน (EC-2) | เปิดแอปและไปที่หน้าของเรื่องนั้นเพียงหน้าเดียว ไม่เปิดหน้าจอซ้อนทับกันหลายหน้า |
| ค่าที่อ่านจากฟีเจอร์อื่นติดลบ หรือ `daily_goal` = 0 (EC-3) | ระบบจะระงับการส่งข้อความแจ้งเตือนของเรื่องนั้น ๆ ในรอบวันนั้นทันที |
| `daily_water_count` เกิน 8 แก้ว เช่น 12 แก้ว (EC-4) | ถือว่าครบเป้าน้ำสมบูรณ์ ระบบจะไม่ส่งข้อความแจ้งเตือนเรื่องน้ำใด ๆ เพิ่มเติม |
| หลายข้อความครบกำหนดส่งพร้อมกัน (EC-5) | ระบบจะทำการจัดลำดับความสำคัญในการส่งคือ อาหาร > น้ำ > เดิน และเว้นระยะห่างตามกำหนด |
| บันทึกน้ำ/อาหาร/มีก้าวใหม่/บันทึกขยับเอง ระหว่างที่ข้อความเรื่องนั้นกำลังรอส่ง (EC-6) | ระบบจะยกเลิกข้อความที่รอส่งของเรื่องนั้นทันที |
| ครบกำหนดส่งข้อความในช่วงเวลาห้ามเตือน (23:00:00 ถึง 05:59:59) (EC-7) | ระบบจะไม่ส่งข้อความใด ๆ ในคืนนั้น และตัวนับจะเริ่มใหม่ตามกติกาหลังช่วงห้ามเตือนสิ้นสุดลง (06:00:00 เป็นต้นไป) |
| ข้ามรอบเวลา 05:00:00 (EC-8) | ระบบจะทำการรีเซ็ตจำนวนข้อความที่ส่งแล้วในรอบวันกลับเป็น 0 และรีเซ็ตสถานะการส่ง "เดิน: ใกล้เป้า" เป็น "ยังไม่ส่ง" |
| กดไม่อนุญาตบนการ์ดความยินยอมแล้วมาเปิดสวิตช์ในหน้าตั้งค่าทีหลัง (EC-9) | แอปจะเรียกกล่องขอสิทธิ์แจ้งเตือนของระบบปฏิบัติการขึ้นมา (ถือเป็นการขอสิทธิ์ครั้งแรกสำหรับผู้ที่เคยกดไม่อนุญาตบนการ์ด) |
| ระบบปฏิเสธสิทธิ์แจ้งเตือน / OS-level Permission Denied (EC-10) | ระบบถือว่าปิดใช้งาน ไม่ส่งข้อความใด ๆ และหน้าตั้งค่า (S-2) จะแสดงข้อความแจ้งเตือนสถานะว่าสิทธิ์ถูกปิดจากระบบ |
| ก้าวข้าม 80% และ 100% ในรอบอัปเดตเดียว เช่น จาก 70.00% ไป 100.00% (EC-11) | ระบบจะไม่ส่งข้อความ "เดิน: ใกล้เป้า" (ตรงตามเงื่อนไข AC-14) |
| ผู้ใช้ตรวจก้าวไม่ได้ (EC-12) | ผู้ใช้จะไม่ได้รับข้อความ "เดิน: ไม่ขยับ" และ "เดิน: ใกล้เป้า" แต่จะได้รับข้อความ "เดิน: บันทึกเอง" แทนตามรอบเวลา 4 ชั่วโมง |
| เปิดแอปจากแจ้งเตือนในสถานะแอปถูกปิดสนิท / Killed State (EC-13) | ระบบจะเปิดแอปขึ้นมาและพาผู้ใช้ไปที่หน้าฟีเจอร์ของเรื่องนั้น ๆ ทันที |
| ไม่เปิดแอปข้ามรอบวัน (EC-14) | จะไม่มีข้อความแจ้งเตือนของรอบวันใหม่ถูกส่งจนกว่าผู้ใช้จะเปิดแอปขึ้นมาใช้งาน เมื่อเปิดแอปแล้ว ระบบจะตั้งค่าข้อความของรอบวันปัจจุบันใหม่ตามกติกาทั้งหมด |
| ส่งครบ 6 ข้อความก่อนเวลา 21:00 (EC-15) | ระบบจะหยุดส่งข้อความเพิ่มทันทีจนถึงเวลา 05:00:00 ของรอบวันถัดไป และข้อความที่เข้าเงื่อนไขระหว่างนั้นจะถูกยกเลิกทั้งหมด |

   - *กติกาชั่วคราวเพื่อให้ Dev พัฒนาต่อได้ทันที (Fallback Rule):* ให้ Dev อ้างอิง Path `assets/images/notification/frog_profile.png` สำหรับแสดงผลบนการ์ด S-1 และ Android Notification Builder ทันที
   - *การประเมินสถานะการบล็อก:* Blocking: ไม่ใช่ (เพราะมีชื่อไฟล์และ Asset กำหนดชัดเจนแล้ว)
~~~~
